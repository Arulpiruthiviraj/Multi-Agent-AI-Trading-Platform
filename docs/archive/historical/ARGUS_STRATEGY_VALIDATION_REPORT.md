## Phase 4 — Walk-Forward Validation: VERIFIED ALREADY REAL, RESULT IS NEGATIVE

`WalkForwardValidator.ts` (extended this same prior session to also drive `runStrategyBacktest()`,
not just the original `run()`) does real chronological train→test window rolling, never randomly
shuffled, with fixed, non-optimized strategy rules identical across every window.

Real result on the two highest-Sharpe rows from Phase 3's table above
(`scripts/runWalkForwardCheck.ts` → `WALKFORWARD_CHECK_RESULTS.json`, `trainDays=365`/`testDays=120`,
21 real rolling periods each):

| Combination | Avg in-sample return | Avg out-of-sample return | IS→OOS degradation | % OOS periods profitable |
|---|---|---|---|---|
| MOMENTUM_BREAKOUT / MSFT | +0.37% | **+0.04%** | -89% | 42.9% |
| MOMENTUM_BREAKOUT / AMD | +1.36% | **+0.28%** | -79% | 66.7% |

**This is a real, negative finding, not withheld or reframed.** Both real out-of-sample returns
collapse to a small fraction of their in-sample counterparts - the textbook in-sample-overfitting
signature. **Not fixed, not re-tuned, not cherry-picked around** - per this phase's own explicit
rule against optimizing until the number looks better, this result is reported as-is.

**Real, honest gap**: only 2 of the 20 real strategy×symbol combinations from Phase 3's table have
been walk-forward checked so far. The other 18 (including the ones with real positive in-sample
Sharpe/expectancy) have **no out-of-sample evidence at all** - a positive in-sample number with zero
external check, which per this phase's own instruction must not be described as validated. Extending
the walk-forward check to the remaining 18 combinations is real, mechanical work (the tooling already
exists and needs no new code) - deferred as a P2 item given this pass's finite scope, not because it
would be hard.

**Bootstrap/permutation tests**: `quant/analysis/MonteCarlo.ts` (real, seeded/deterministic bootstrap
resampling over a completed backtest's R-multiples, always labeled `scenarioAnalysis:true`, never a
prediction) exists as tooling but has not yet been run as a formal significance test against any of
the walk-forward results above - also a real, deferred P2 item, not fabricated as done.

## Phase 5 — Strategy Selection Architecture: VERIFIED ALREADY REAL

The exact anti-pattern this phase warns against ("RSI=vote, MACD=vote, SMA=vote... these are
correlated") is explicitly avoided, not accidentally avoided:

`quant/scoring/GroupedScores.ts` blends RSI/Stochastic-RSI/CCI/Williams %R into **one** oscillator
reading (they measure the same overbought/oversold latent factor), separately blends MACD/ROC into a
**second**, genuinely-different-methodology reading, then combines those two 50/50 - never treating
4-6 individual indicators as independent votes. A dedicated test
(`GroupedScores.test.ts`) asserts 4 agreeing oscillators score only modestly higher than 1 agreeing
oscillator (bounded, not linearly amplified) - proving the blending, not just claiming it.

The real pipeline already matches this phase's own requested architecture:

```
Feature engineering (quant/indicators/*.ts, real trend/momentum/volatility/volume/support-resistance)
        v
Market regime (RegimeEngine.ts - multi-signal, never a single indicator)
        v
Strategy selection (StrategyEngine.evaluateAll() - discounts, never zeroes, a strategy's confidence
                     when the current regime doesn't match its own applicableRegimes)
        v
Strategy score (each strategy's own setupScore/confidence from GroupedScores.ts)
        v
Probability/expectancy (ExpectedValue.ts - see Phase 6 below)
        v
Risk validation (RiskEngine.ts - see ARGUS_SAFETY_HARDENING_REPORT.md)
        v
Chief Trader (EvidenceAggregator.ts weighted vote, real Beta-Binomial calibration)
```

Deterministic calculations remain the quantitative backbone throughout; the one real AI integration
point (`quant/ai/QuantContradictionAnalyzer.ts`) can record a disagreement but never overwrite a
deterministic side/confidence value - verified by direct code read, not assumed.

## Phase 6 — Risk / Expected Value Engine: VERIFIED ALREADY REAL

`quant/risk/ExpectedValue.ts` computes real risk/reward ratio, expected value (in R), and fractional
Kelly, directly from a completed backtest's own real win rate and R-multiples - never an assumed or
guessed probability. Refuses to suggest a Kelly fraction below 20 real closed trades
(`MIN_SAMPLE_SIZE_FOR_KELLY`), and hard-caps its own suggested fraction at 10% of capital regardless
of what the raw formula computes (`MAX_KELLY_FRACTION_OF_CAPITAL`) - demonstrated live on
MEAN_REVERSION/AMD above, where a real negative edge correctly produces a 0% Kelly suggestion, not a
suppressed-but-nonzero one.

**AI does not override this layer.** `QuantContradictionAnalyzer.ts`'s output is a separate,
additive field (`disagreementNote`) never fed back into the EV/Kelly calculation itself.
`RiskEngine.ts`'s own hard caps (position/sector/correlation limits, circuit breakers) remain
authoritative over anything this layer suggests - confirmed structurally in
`ARGUS_SAFETY_HARDENING_REPORT.md`'s independent trace of the consensus→risk chain.
