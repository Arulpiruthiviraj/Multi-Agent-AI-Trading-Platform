# Engine freeze triggered by an operator diagnostic report - 2026-10-14

Status labels: VERIFIED = observed in logs/tests, INFERRED = strong code-level evidence, not reproduced on the live engine.

* VERIFIED: at ~12:48:35 ET the production engine (3a5eacdc, pid 19784, supervised PAPER, flat, no open orders) stopped answering /health. Watchdog: SUSPECT 1/10 ... 9/10 then FROZEN_CONFIRMED at 12:54:37 ET, force-restart via `argus-cli start` (no --enable-trading). Engine returned paused, reconciliation MATCH, no positions; resumed through the normal `resume` path at ~12:56 ET.
* VERIFIED: the freeze began within seconds of a burst of read-only CLI report commands (`trading-funnel, quant-readiness, strategy-readiness, missed-opportunities, discovery-challengers, rescue-outcomes, ...`) issued by the operator session; the first four completed, subsequent ones timed out.
* INFERRED (root cause): `GET /api/v2/observability/rescue-outcomes` ran three synchronous better-sqlite3 queries PER rescue grant (N+1) on the engine event loop, and was not wrapped in `guardHeavyReport`. With ~600 rescue requests in a normal session (production had 84 rescue holders / ~85% renewal) that is thousands of full-table-window scans.
* Fix (branch fix/oct14-report-freeze): `buildRescueOutcomeReport` now issues a constant 4 queries (1 grant query + 3 batched correlation queries, chunked at 500 symbols); route-level `guardHeavyReport` added for `rescue-outcomes` and `discovery-challengers` (serialised, memory breaker, 429 on refusal). Regression test asserts the query count is constant (old implementation: 910 queries for 300 grants; new: <= 8).
* Limits (honest): the underlying better-sqlite3 calls remain synchronous on the main thread, so a very large window can still stall the loop briefly; moving these reports to `selectRowsOffThread` is a follow-up. Not yet reproduced against the live DB size. Other unguarded report routes (41 observability routes, 5 guarded) have not been audited yet.
* Impact: no positions or orders were exposed; the session had no entries. In a session holding positions, a multi-minute loop stall would delay software-resident protective exits - this is a P0 class defect for operator tooling.
