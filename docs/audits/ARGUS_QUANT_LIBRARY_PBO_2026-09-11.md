# PBO / CSCV — Source Reading Note (2026-09-11)

Source read in full: `Bailey, Borwein, López de Prado, Zhu — "The Probability of Backtest Overfitting"` (revised Feb 2015; SSRN 2568435), `C:\WorkProjects\quant-resources\THE PROBABILITY OF BACKTEST OVERFITTING.pdf`, 34 pages. Read directly (not summarized from memory or title).

## 1. What the paper actually says

**The problem (§1, pp.3-8).** Testing many strategy configurations on one finite dataset and picking the best in-sample (IS) result manufactures false positives almost certainly, even at a nominal 95% significance level, because that 5% only holds for a single test — not for the billions of parameter combinations a researcher can trivially sweep. The paper explicitly rejects the "hold-out" (train/test split) method as the standard fix: hold-out data is often contaminated by prior researcher knowledge, is statistically underpowered on realistic sample sizes (Weiss & Kulikowski's ≥1,000-observation rule, p.7), has high-variance outcomes depending on which slice is withheld, and — critically — ignores the number of trials attempted (p.7, citing their own companion paper for a proof).

**The definitions (§2.1, pp.9-10).** The paper builds a formal framework: for N strategy configurations, compare each strategy's in-sample (IS) rank against its out-of-sample (OOS) rank. **Backtest overfitting** is defined as the event that the strategy with optimal IS rank has an *expected* OOS rank below the median (Definition 2.1, eq. 2.1, p.9). The **Probability of Backtest Overfitting (PBO)** is then the actual probability estimate of that event (Definition 2.2, eq. 2.2, p.10) — a Bayesian posterior probability given the empirical IS/OOS evidence, not a claim that overfitting is itself a random event (p.6).

**The CSCV procedure (Algorithm 2.3, §2.2, pp.10-13) — the real, implementable steps:**
1. Build matrix **M** (T rows × N columns): each column is one strategy configuration's P&L/return series over T synchronized observations.
2. Partition M's rows into an **even number S** of equal-size, contiguous, non-overlapping submatrices M₁...M_S (each T/S × N). The paper recommends **S = 16** as a practical default (p.22): it yields C(16,8) = 12,870 combinations (correcting a transcription error from the initial reading pass — independently verified as 16!/(8!·8!) = 12,870, and confirmed programmatically by `computePbo()`'s own `combinationsOf()` in `src/server/research/pbo.ts`, plus a dedicated unit test asserting exactly this count), keeps the standard error of the estimated PBO below ~0.0045 (95% CI width <0.01), and — for roughly 4 years of daily data — each slice spans about a quarter, preserving serial/seasonal structure. (For 6+ years of data they instead suggest S=24; for coarser quarterly structure, S=12 or doubling T.)
3. Form **all C(S, S/2) combinations** of the S slices taken S/2 at a time (eq. 2.3). For each combination c: join the S/2 chosen slices (in original time order) into **training set J**; the complementary S/2 slices (also in original order) form **testing set J̄**. Both are size T/2 × N — deliberately equal-size, unlike hold-out.
4. On J, compute the chosen performance statistic (paper uses Sharpe ratio, but states explicitly the method works with any metric — Sortino, Probabilistic Sharpe Ratio, etc.) per column, rank the N strategies, and find n*, the IS-optimal strategy for that combination.
5. On J̄, compute the same statistic for all N columns, find strategy n*'s **relative OOS rank** ω̄_c = r̄_c,n* / (N+1) ∈ (0,1).
6. Compute the **logit** λ_c = ln(ω̄_c / (1 − ω̄_c)). High logit ⇒ the IS-optimal strategy also ranked well OOS (good sign); logit near/below 0 ⇒ it did not.
7. Repeat for all combinations in C_S, producing a distribution of logits f(λ).
8. **PBO = φ = ∫₋∞⁰ f(λ) dλ** — the fraction of combinations where the IS-optimal strategy's logit was ≤ 0, i.e. it underperformed the median OOS despite being "best" IS (§3.1, p.13-14).

**Decision rule given by the paper (p.14):** "a customary approach would be to reject models for which PBO is estimated to be greater than 0.05" (the paper's own suggested analogy to a 5% significance threshold — not a hard law, just their stated convention). The paper also flags PBO can be used as a Bayesian prior, or to weight a multi-strategy portfolio by (1 − PBO) or 1/PBO. Companion diagnostics from the same CSCV output, cheap to compute alongside PBO: **performance degradation** (regression of OOS-SR on IS-SR — a real, worked example in the paper shows slope β=−0.75, meaning higher IS Sharpe predicted *lower* OOS Sharpe, p.14-15), **probability of loss** (Prob[OOS SR < 0]), and **stochastic dominance** (does the IS-selection procedure's OOS distribution actually beat picking a strategy at random — first- and second-order tests, §3.3, pp.17-19).

**Honestly stated limitations (§5, pp.23-25) — important, not boilerplate:** CSCV can obscure structure if S is set too large relative to real autocorrelation in the series; it weights all sample statistics equally, which is only "natural" absent prior information; it says nothing about whether a backtest's *assumptions* were correct (bad transaction-cost/slippage/look-ahead modeling still passes through untouched); it can't detect a structural break outside the tested window; a high PBO can appear even among genuinely skillful strategies if many of the N configurations are all similarly good (indistinguishable, not bad); and — the paper's most pointed warning — **CSCV must never be used as the objective function to guide strategy search itself** ("when a measure becomes a target, it ceases to be a good measure," p.25) — it is an ex-post reliability audit, not an optimizer.

## 3. Concrete, scoped next step

A standalone, **default-off, offline** script (e.g. `scripts/compute_pbo.ts`, following the existing `scripts/organic_paper_soak_status.ts` pattern: opens SQLite, computes, exits — never a long-running process, never imported by any live-path file):

- Input: a strategy family's rows from `quant_strategy_backtests` (grouped by `strategyId`/regime, or a caller-supplied set of N run ids representing N configurations of the same idea), reconstructing each configuration's per-period return series from `equityCurve`/`tradeLog`.
- Requires ≥2 rows to form matrix M's columns (N ≥ ~10 recommended per the paper's own granularity argument, p.22) and enough synchronized observations T to pick S=16 sensibly.
- Implements exactly Algorithm 2.3 above: partition, C(S,S/2) combinations, per-combination IS/OOS Sharpe + rank + logit, PBO = φ = fraction of logits ≤ 0.
- Output: a printed/JSON report (PBO, performance-degradation slope, Prob[OOS<0], stochastic-dominance check) — **additive only**, never written back into a table any gate or `evaluateLiveReadiness()` reads, never wired into `ChiefTraderAgent`/RiskEngine/OMS, and explicitly not exposed as a live "confidence adjuster." This mirrors `researchSafety.json`'s existing framing (soak/OOS/WFO floors are "research, not live knobs").
- If it proves useful, a small persisted table (e.g. `pbo_assessments`) could follow later — deliberately not proposed here; the script alone is enough to learn whether PBO says anything interesting about the ~150+ existing strategy/config combinations before investing in a schema.

This is a measurement tool addressing CLAUDE.md's own stated gap ("no PBO/deflated-Sharpe/purged-cross-validation methodology exists... today") — not a rewrite of any existing engine, and does not touch `src/server/quant/` or `quant-core-java/` calculation code at all.

## 4. What would NOT directly apply to Argus as-is

- **The paper assumes T is large enough to split into S=16+ slices while preserving statistical validity of the per-slice Sharpe ratio** (IID-Normal-ish assumption per slice, p.11). Most of Argus's live/paper strategies have **zero or near-zero organic closed trades** (`CLAUDE.md`: "Organic PAPER FILLED SELL P&L: 0 / 30 trades"), so CSCV is only meaningful today against **backtest** output (`quant_strategy_backtests`), not live/paper track record — exactly the caveat the paper itself makes about MinTRL/minimum track record length in its companion work.
- **The paper's worked examples use daily-bar, multi-year synthetic and real series** (~1,000 daily observations, §6). Argus's CORE strategies and many experimental ones have not been validated with that much clean OOS history yet (`CLAUDE.md`: "Walk-forward OOS for checked quant combos failed").
- **CSCV says nothing about backtest correctness** (§5.2, explicitly, p.24) — it cannot catch Argus-specific concerns like look-ahead bias, unrealistic fill assumptions (`BacktestEngine.ts` is `SAME_BAR_CLOSE`, explicitly non-promotable per `CLAUDE.md`), or slippage. A low PBO on a flawed backtest is not proof of edge.
- **The paper's N (number of trials/configurations)** assumes an explicit, *fully declared* parameter sweep (§5.2's "file drawer problem" warning: hiding trials biases PBO downward). Argus would need to honestly enumerate every configuration actually tried per strategy family — `experimentLedger.ts`'s trial counter already exists for exactly this purpose and would need to be the source of N, not a fresh guess.
- **The paper explicitly warns against using PBO itself as a search/optimization objective** (p.25) — a rule any Argus integration must respect: PBO must stay a read-only audit stat, never fed back into strategy selection/tuning logic, which would recreate the exact overfitting problem it's meant to detect.
