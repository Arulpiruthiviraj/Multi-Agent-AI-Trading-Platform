Defects found and fixed

All three real, all regression-tested pre/post, each proven by reverting the fix and watching the exact original failure reproduce. Ranked by consequence, not discovery order.
Defect 1 of 3 — most consequential

Stale-price selection in consensus math

What broke: when two agents with different evaluation cadences (a fast tick-driven agent and a slower, cooldown-throttled one like Kronos) agreed in the same consensus round, the system picked whichever agent's price happened to sit first in an internal list — not the fresh, triggering agent's price. In the reproducing case the stale price was 143 simulated minutes old.

Why it mattered: this fed directly into RiskEngine's own capital and notional-sizing math — a real risk-decision-quality defect, not a cosmetic logging inaccuracy. It understated one real trade's notional by roughly 5%. This is general production consensus code, not synthetic-only.

Fix: the approval path now prefers the triggering idea's own price, falling back to the old behavior only when that price is missing — the same fallback pattern an adjacent code path already used safely. No threshold, weight, or vote-counting change.

Reproduced"expected 246.79 to be 259.89" — before the fix
Regression tests2 new cases, both directions verified
Defect 2 of 3

Synthetic sessions silently reading real market data

What broke: the Java quant ensemble's data path had no isolation guard on its real-network fallback. Every synthetic certification run this whole effort made a live Alpaca API call and evaluated real, historical SPY/QQQ/AAPL daily price history instead of the synthetic scenario — never touching production's own database, but silently contaminating every synthetic run's evidence.

Why it mattered: it explains why that agent voted the same bearish direction on every seed regardless of the programmed scenario, and it invalidated every earlier finding in this report that depended on its output — marked PRE-FIX / INVALID below rather than quietly carried forward.

Fix: the real-network fallback now refuses to fire during a synthetic session and fails loudly instead of silently substituting real data — the same "disable, don't fabricate a stand-in" principle already used elsewhere in this codebase.

Regression tests2 new cases, both directions verified
Safety impactNone — production database was never touched
Defect 3 of 3 — found while building new coverage, not a leftover

Duplicate market events could double-fill an order

What broke: while adding the ability for a partially-filled synthetic order to keep filling as later market bars arrive, an adversarial test — calling that new completion step twice without the clock actually advancing, simulating a duplicate tick — showed it filling 300 shares against a single bar's own 100-share volume cap. Each call independently recomputed the cap with no memory of already having consumed it once.

Why it mattered: this is exactly the "duplicate market event" failure class flagged as an open risk in this report's own remaining-work list — reproduced on the very first real attempt to exercise it, not a defect that sat undiscovered.

Fix: each order now remembers which bar it last advanced on; a repeat call at the same bar is a true no-op, and a genuinely new bar still fills normally.

Reproduced300 filled against a 100-share single-bar cap — before the fix
Regression testsBoth directions verified, plus the full entry-through-exit lifecycle proven around it

Full chronological record

This report was built across several same-day passes as an internal engineering log — later findings sometimes correct or supersede earlier ones. Everything below is preserved for audit value; the sections above this point are the current, authoritative state. Tap any entry to expand it.

Phase 1 — Initial synthetic certification (Test A / Test B)Marked PRE-FIX / INVALID — ran before the data-isolation defect was found

Test A — no-edge safety control

Verdict: pass. Scenario QUIET_OPEN, calibration seeding off. Zero trades, with a real, legible, non-threshold-related reason (no idea ever reached independent multi-agent agreement) — the correct, expected outcome for a no-edge scenario.

Test B — controlled tradeable scenario

Verdict: fail (did not complete the full entry → fill → position → exit → P&L lifecycle). 37 real ideas were generated. A real scenario bug was found and fixed along the way: the original volatility profile was too low relative to its drift, pinning RSI at 85–97 for the whole session — agents correctly read an over-extended ramp as overbought, which was not a bug in the agents. Raised the volatility multiplier; confirmed post-fix that TechnicalAgent genuinely fired healthy momentum BUY ideas with RSI in the 65–70 band.

Consensus still never triggered at those exact BUY moments — no second independent agent's vote landed in the same debate window as TechnicalAgent's own read.

Rule 5 follow-up — a real diagnostic correction

A direct re-check found the earlier "37 ideas" accounting had conflated 25 synthetic calibration-seed rows with real session predictions. The actual run had zero real JavaCoreEnsemble predictions and zero real KronosEngine predictions that run — the local Chronos AI service and the Java Quant Core HTTP server were simply never running alongside the simulator. Both agents behaved exactly as designed when their backing service is down (fail-closed, not fabricated) — a simulator-completeness gap, not an agent defect.

Starting both real backing services and re-running gave, for the first time, genuine three-independent-family data: real convergence occurred (JavaCoreEnsemble + TechnicalAgent on SPY SELL; KronosEngine + TechnicalAgent on QQQ SELL, both repeatedly, within about a second of each other). The system still correctly declined to trade, for two real reasons: the weighted confidence never cleared the 0.75 STRONG bar (capped near JavaCoreEnsemble's own flat 0.65), and the newly-converging agent's calibration bucket wasn't yet trusted — both intentional, already-documented safety mechanisms operating correctly on real data.

Seeded vs. unseeded certification

Re-run with zero synthetic calibration history (the same "brand-new deployment" state a real production instance starts from): real independent agents converged and reached 0.7397 raw confidence — within 0.01 of the STRONG bar — with the calibration-trust gate the only reason nothing traded. A zero-history deployment cannot yet pass MODERATE-tier trust by design, regardless of how well its agents agree; that gap only closes with real elapsed calibration history, not a threshold change.

Confidence-ceiling audit

Source-level audit found no hardcoded confidence literal anywhere in the Java ensemble's dispatch path — the flat 0.65 reading was, at the time, believed to be a genuine reflection of an unchanging setup on that symbol. This conclusion is later superseded once the data-isolation defect was found: the setup being read was never the synthetic scenario at all.

Determinism fix — real root causes found and fixedNewsEngine/AI-provider isolation closed; one smaller nondeterminism left open

A same-seed run executed twice showed identical bar/analysis-cycle counts but different news-cluster and prediction counts. Root cause: the real NewsEngine and FundamentalAgent/MacroAgent ran on their own real-time schedules independent of the synthetic session's own deterministic providers — a separate, redundant, real-network background loop kept writing non-deterministic rows alongside the correct synthetic path.

Fixed at two independent call sites (a first pass found and fixed only one; a same-seed re-check caught the second) plus explicitly disabling FundamentalAgent/MacroAgent during synthetic sessions, since they make real AI-provider calls with no synthetic equivalent — the honest fix is to not run them, not fabricate a deterministic stand-in.

Verified before/after: news clusters and non-TechnicalAgent predictions dropped to zero and stayed zero, deterministically, across repeat runs.

One smaller issue was found and left open, stated plainly: the indicator math itself was proven fully deterministic to the byte across 240 compared analysis cycles — the remaining divergence is confined entirely to which exact cycle "wins" a signal-emission decision when a condition is satisfied on multiple consecutive bars, a suspected real async/event-loop scheduling-order effect, not yet confirmed or fixed.

The "LIVE refused" defect — root-caused and fixedThe reason no synthetic order had ever completed a fill, all mandate long

A seeded run reached, for the first time, a genuine consensus approval, a genuine RiskEngine approval, and a real order-submission attempt — the deepest the pipeline had reached yet — but the order came back stuck, with the broker reporting Error: LIVE refused.

Root cause, traced to source: the synthetic broker's own safety self-check — which proves a synthetic session's broker is structurally incapable of a real order by calling its "go live" method and confirming it throws — was calling that method on the same broker instance the session then used for every real order for the rest of the run. The safety check's own proof call was permanently poisoning the exact broker it had just certified. Every synthetic session this entire mandate had run was structurally incapable of ever completing a fill, no matter how far a scenario otherwise progressed.

The poisoning flag added no real protection it didn't already have — the "go live" method already unconditionally threw on every single call, with or without it. Removed the flag; the "cannot go live" guarantee is unchanged and still holds on every call.

Reproduced directly both ways: reverting only the fix reproduces the exact original failure; restoring it passes. Two post-fix reruns showed zero recurrences, reaching only legitimate downstream rejections instead.

Major finding — synthetic sessions were reading real market dataThe isolation defect that invalidated everything before it

Prompted by one striking pattern: the Java quant ensemble voted the same bearish direction on literally every one of roughly 500 votes across 6 seeds of a scenario that was about 68% genuine sustained uptrend by design. That pattern turned out not to be organic — it was a real, undisclosed isolation defect.

Root cause: the Java-ensemble evaluation path computed its data window from the real wall clock and always requested daily-scale bars — a timeframe the synthetic engine never writes at all (it only ever writes minute-scale synthetic bars). Direct query of a completed session's own isolated database confirmed both halves at once: 275 real daily SPY rows dated Aug 2025–Sep 2026 sitting alongside 240 genuine synthetic minute rows for the same symbol in the same database.

Because the evaluation path's local cache was insufficient, it fell through to a real, live historical-data API call using this process's real credentials — credentials that were never stripped from the synthetic session's environment. Because every synthetic run gets a brand-new, empty database, this happened on every single run this entire mandate. This never touched production's own database — the real data landed only in that run's own isolated file — but it silently invalidated every finding upstream of it in this report that depended on that agent's output.

TechnicalAgent was never affected — it reads from a separate, correctly-isolated live-tick path, which is exactly why its readings tracked the synthetic scenario's real shape while the Java ensemble's never did.

Fix: the real-network fallback now refuses to fire specifically during a synthetic session and fails loudly instead of silently substituting real data. Scoped narrowly so it doesn't also break the ordinary test suite, which legitimately exercises the same code path against mocked data.

Effect, observed directly: rerunning post-fix immediately changed the picture. One rerun: the contaminated agent's vote count dropped from 88–92 per run to zero — correctly silenced. Another rerun, same scenario, same fix: produced the mandate's actual objective for the first time — a genuine independent-agent agreement, a genuine RiskEngine approval, and a real filled order. Honest limitation at the time: that particular fill happened late enough in the session that no exit could fire before the session ended — the entry half was proven; the exit half was not yet.

Final certification pass — the stale-price defect and the first complete lifecycleSecond defect found while verifying the first fill's price honestly

While tracing exactly how the first post-fix fill's price was calculated — per an explicit instruction not to call a fill "realistic" without showing the actual math — the trade's recorded arrival price didn't match the triggering idea's own price, confirmed byte-exact against the real bar the idea came from. That mismatch led directly to the stale-price consensus defect described above.

Scenario timing, redesigned from real evidence

Two sequential findings drove a real scenario-timing fix, not a guess: first, the genuine entry kept firing from a late-session reversal phase rather than an early one, because the original mid-session consolidation never gave the technical read an early dip to trigger on — so a real, bounded early pullback was added. Second, two further runs showed the entry still firing from the late reversal phase regardless — the forecasting agent needed more sustained trend data than a brief dip provides. In the process, a real mechanical detail was found: any simulated time past a scenario's last defined phase silently falls through to a flat, uninformative default, which is why an earlier attempt to simply run a longer session without extending that phase's own boundary produced a misleading result. The actual fix was extending the reversal phase itself so a late-firing entry has real continued-reversal room afterward — not a fabricated exit rule, the same pre-existing mechanism, just given room to matter.

Fill-price mechanics, shown exactly

Solved backward from the recorded fill price: the broker's own reference price for both the entry and the exit fill matched the recorded arrival price exactly, with the entry/exit prices differing only by the small, fully disclosed spread-and-slippage cost model — not a mystery gap. Concluded precisely: this fill is genuinely next-bar-open pricing plus a small, configured cost model, demonstrated rather than merely asserted, and it explicitly does not model order-book depth, liquidity, or latency.

What remained open at the end of this pass

  • Only 2 of 5 seeds produced the complete lifecycle that pass — reported exactly as observed, not rounded up.
  • The full 20-item adversarial fault-injection matrix (broker disconnects, partial fills, restarts, duplicate/out-of-order events, and more) — none built yet; each needs new fault-injection mechanics the synthetic broker didn't have.
  • Restart-mid-position and broker-disconnect handling — not yet tested against the real synthetic broker specifically.
  • Deeper event-loop and memory instrumentation beyond coarse RSS sampling — not yet added.

Explicit operator correction carried into every section since: readiness was split into three separate claims rather than one blanket "ready" line — paper-trading engineering readiness, real-money readiness, and live-alpha validation are not the same question and must never be collapsed into each other. And the status vocabulary was tightened so a missing test only ever reads as NOT CERTIFIED or NOT IMPLEMENTED, never as an ordinary FAIL — that word is reserved for an actual demonstrated defect, and none of the outstanding items are one.

Final autonomous pass — closing the highest-value remaining gapsRestart-mid-position and broker-disconnect proven; zero new defects found

The most recent pass closed real, previously-disclosed coverage gaps with genuine integration tests against the actual synthetic broker — not stand-ins — and surfaced instrumentation the engine already computed but had never printed.

  • Restart-mid-position, previously the single largest named gap: a real BUY placed through the actual synthetic broker, local state deliberately cleared to simulate a restart's real failure mode, recovery run through the unmodified production reconciliation code, then a real exit against the recovered position — no duplicate entry, correct recovered quantity and price, no duplicate exit, correct realized P&L.
  • Broker disconnect / unknown state: a real broker call made to throw mid-submission (a genuine disconnect simulation). Proved directly, not by inspection, that the order stays pending rather than being fabricated as filled or rejected, that trading actually pauses, and that no blind retry occurs.
  • Event-loop and memory instrumentation, already computed by the engine but never printed, now surfaced: over a full 400-simulated-minute run, event-loop delay stayed at p50 75 ms / p95 114 ms / p99 142 ms / max 225 ms with no runaway pattern in either that or memory — read honestly as a batch-simulation workload's own numbers, not a live-latency claim.
  • The two existing memory-safety mechanisms from an earlier incident (an overlap guard against concurrent evaluator runs, and a bounded, cooldown-gated heap-snapshot capture that never delays the real trading-pause safety response) were reconfirmed intact by direct source inspection, untouched.
  • One previously-ambiguous seed was cleanly reclassified under the corrected scenario as a legitimate rejection rather than an open question.

Zero new defects were found this pass. The two defects described above remain the only real engineering defects this entire certification effort uncovered. No production safety boundary was touched, and no consensus, calibration, weighting, threshold, or risk parameter was changed at any point.

Production's canonical headless-startup command was confirmed directly from the project's own documentation rather than re-executed — restarting an already-running, already-healthy production process purely to re-demonstrate a command already proven safe earlier the same day would have been an unnecessary disruption, reserved for when it's actually required.

Partial-fill completion pass — the last open item, closedOne new defect found while building it, fixed in the same pass

This pass built the one piece of real engineering scope the previous pass had explicitly deferred: a partially-filled synthetic order previously froze at its first-bar quantity forever — no real broker behaves that way. The synthetic broker now lets a resting order keep filling as later bars bring more liquidity, using the exact same pricing, cash, and position-update logic its very first fill already used — wired into every real synthetic session, not just callable from a test.

Adversarially testing that new mechanism surfaced defect 3 of 3, above, on the first real attempt — found and fixed in the same pass, not carried forward as a known gap.

Full lifecycle proven through the real broker: a BUY capped at 100 of 300 shares on bar one completes the remaining 200 on bar two; the order-management layer's own pre-existing fill-aggregation logic (already proven correct against a stand-in broker in an earlier pass) correctly records the second increment without re-counting the first or inventing a third; the resulting position reflects the full, correctly-averaged 300 shares; a clean subsequent sale exits it with a real, correctly-computed gain and a fully flat final state. A companion case proves the honest failure mode too: an order that never gets a chance to complete stays truthfully partially filled forever, never silently marked done.

Before building anything new, the existing test suite was surveyed rather than assumed empty — several other items on the remaining-work list turned out to already have real, thorough coverage at the general order-management and reconciliation layer (mismatch detection and pause escalation, hostile AI-output handling, concurrent-evaluator prevention, memory-pressure pause), just not exercised through the synthetic broker specifically. Full suite: 517 files, 3,800 tests, all passing. Production reconfirmed untouched throughout.
